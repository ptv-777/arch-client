# План завершения DICOM-архива

Статус: pre-alpha. План составлен по текущему коду, текстовому ТЗ и переписке
за ноябрь 2025 — июль 2026. До выполнения этапа 0 реальные медицинские данные
в тестовый контур не загружать.

## Решение по репозиториям

На текущем этапе нужен один монорепозиторий для сервера, ingest-worker,
контракта API, клиента и развёртывания. Команда и кодовая база малы, релизы
клиента и API связаны, а фактический сервер уже находится в `arch-client`.

`arch-serv` следует оставить read-only как исторический прототип, затем
архивировать после переноса полезных решений. Разделение снова имеет смысл,
если появятся независимые команды, разные права доступа или независимые циклы
релизов. Общее DICOM-ядро при этом должно оставаться отдельным пакетом с
версионируемым API-контрактом.

## Целевая схема

- NAS хранит DICOM-файлы и резервные копии, но не исполняет бизнес-логику.
- Linux-сервер выполняет индексирование, ingest, дедупликацию, упаковку и API.
- СУБД использует отдельную базу, отдельного пользователя и минимальные права.
  Использовать схему или учётную запись другого продукта нельзя.
- Клиент обращается только к API. Прямого доступа врачей к СУБД и NAS нет.
- Windows-клиент запускает RadiAnt. Для RED OS нужен отдельно подтверждённый
  просмотрщик или протестированный способ запуска; команда задаётся адаптером.
- API доступен только из доверенной сети, с TLS, аутентификацией, ролями и
  журналом обращений к исследованиям.

Физическое хранилище рекомендуется делать неизменяемым и UID-ориентированным:
`study/series/SOPInstanceUID.dcm`. Требуемое представление
`ФИО/дата/номер/тип/IMG_XXXXX.dcm` лучше материализовать как управляемое
представление или экспорт. Иначе исправление ФИО или даты потребует массового
перемещения файлов и усложнит восстановление после сбоя. Если обязательна
именно физическая человекочитаемая структура, это должно быть отдельным
решением с миграционным журналом и откатом.

## Этапы

### 0. Безопасность и инвентаризация

- Сменить реквизит, попавший в историю `arch-serv`.
- Закрыть публичный доступ к репозиториям, если политика организации не
  разрешает открытый исходный код этой системы.
- Сделать проверяемую резервную копию архива и тест восстановления.
- Подготовить обезличенный набор: корректные DICOM, `DICOMDIR`, повреждённые
  файлы, дубли, разные кодировки ФИО, конфликт пола/даты, ZIP и ISO.
- Зафиксировать объём файлов, число inode, скорость NAS и окно фоновой нагрузки.

Критерий готовности: секрет сменён, тестовые данные обезличены, восстановление
копии проверено, исходный архив не изменяется приложением.

### 1. Инженерная основа

- Оставить монорепозиторий, переименовать его после согласования.
- Разделить зависимости server/client/dev и добавить воспроизводимую сборку.
- Ввести Alembic-миграции, структурированные логи, метрики и health/readiness.
- Добавить CI для Linux и сборочные проверки Windows-клиента.
- Описать версионируемый OpenAPI-контракт и ошибки API.

Критерий готовности: чистая установка поднимается одной инструкцией; миграции и
тесты проходят в CI; конфигурация и секреты не хранятся в Git.

### 2. Read-only индекс существующего архива

- Индексировать текущие пути без перемещения файлов.
- Читать заголовки без pixel data, но валидировать DICOM preamble/метаинформацию
  и обязательные UID.
- Хранить исходный путь, размер, mtime, SHA-256 файла и результат проверки.
- Добавить пациентов, альтернативные имена, исследования, серии, экземпляры и
  конфликты. Пустой `PatientID` не должен объединять разных людей.
- Реализовать идемпотентное продолжение обхода после остановки.
- Дать клиенту поиск и получение ещё не упакованного исследования через API.

Критерий готовности: повторный запуск не создаёт дублей; контрольная выборка
совпадает с архивом; ни один исходный файл не изменён.

### 3. Журналируемый ingest из `+++`

- Источники: каталог, ZIP и ISO; каждый источник получает `ingest_job` и
  состояния `discovered → validating → staged → committed/conflict/failed`.
- Распаковывать во временный каталог с лимитами размера, числа файлов и
  защитой от выхода за каталог.
- `DICOMDIR` учитывать как служебный файл и не импортировать как экземпляр.
- Считать SHA-256, проверять SOP Instance UID и отмечать ситуацию, когда один
  UID имеет разные байты.
- Русское ФИО брать из имени входной папки/источника и сохранять как alias;
  значения DICOM не затирать.
- Необратимое удаление не-DICOM из новых источников включать только отдельной
  политикой после приёмки. До этого использовать карантин и срок хранения.
- Коммитить БД и файлы так, чтобы повторный запуск безопасно продолжал задачу.

Критерий готовности: принудительное завершение на каждом состоянии с последующим
запуском не теряет и не дублирует файлы; конфликт не меняет основной архив.

### 4. Канонизация и конфликт-менеджмент

- Определить приоритет тегов для даты исследования, номера и описания серии.
- Реализовать правила пола/даты рождения и явный конфликт вместо угадывания.
- Добавить очередь ручной проверки и причину каждой метки `!`.
- Создавать человекочитаемое представление только из подтверждённых записей.
- Мигрировать существующие данные пакетами с журналом, dry-run и сверкой хэшей.

Критерий готовности: отчёт до/после сходится по числу файлов и хэшам; любой
пакет можно повторить; неоднозначные записи остаются в очереди проверки.

### 5. Выдача, кэш и клиент

- Упаковывать исследование без коллизий имён, атомарно и с манифестом.
- Добавить контрольную сумму содержимого, HTTP Range и продолжение `.part`.
- Ограничить серверный и локальный кэш по размеру/LRU; не удалять открытое или
  незавершённое исследование.
- Перенести сеть и распаковку из GUI-потока, добавить отмену и понятные ошибки.
- Автоматически открыть только что загруженное исследование в выбранном viewer.
- Собрать и подписать установщики для фактических версий Windows и RED OS.

Критерий готовности: загрузка продолжается после обрыва; хэш проверяется до
открытия; нехватка места не повреждает кэш; одинаковый сценарий проходит на
обоих целевых ОС.

### 6. Защита и ввод в эксплуатацию

- Аутентификация, роли, минимальные права и аудит поиска/скачивания.
- TLS между клиентом, API и СУБД; секреты через системное хранилище.
- Резервное копирование БД, конфигурации и манифестов; регулярный restore-test.
- Нагрузочные тесты на реальном профиле исследования и план обслуживания.
- Приёмка с сисадмином и врачами, инструкция эксплуатации и отката.

Критерий готовности: утверждённая модель угроз и доступов, восстановление
проверено, приёмочные сценарии подписаны, есть мониторинг и ответственный.
